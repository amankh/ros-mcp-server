## #399: Fix concurrent action result correlation

**Recommendation: request changes (one test), then merge first.**

### What I tested

1. **Live repro of #397 (Jazzy).** Two overlapping `send_action_goal` calls through the FastMCP in-memory client. Server: `action_tutorials_py` Fibonacci, orders 10 and 5, second call 0.2 s after the first. 12 tries per branch.

   | Branch | Results with the wrong sequence |
   |---|---|
   | `develop` | 14 of 24 (7 of 12 tries swapped both results) |
   | #399 | 0 of 24 |

2. **A second bug that #399 also fixes.** On `develop`, any other tool call during a running goal loses the goal's result. Test: start a 12-step goal, call `get_action_status` 3 s later. The goal returns `Action timed out after 30.0 seconds`, while the server succeeded. This happened in 3 of 3 tries. With #399: 3 of 3 succeeded. This is probably the cause of #318 (time-out although the action succeeds).
3. **The new unit tests fail on `develop`** (5 failed), so they really reproduce the bug. On #399: 24 passed.
4. **Integration tests:** 1 failure on Humble, Jazzy and Lyrical:
   `test_actions.py::TestCancelActionGoal::test_cancel_request_sent` → `KeyError: 'success'`.

### Review comment

> Thanks, this fixes #397 for me. I reproduced it live on Jazzy with two concurrent Fibonacci goals: on develop 7 of 12 runs swapped the results, with this branch 0 of 12. It also fixes a related problem: on develop, any other tool call during a running goal (for example `get_action_status`) closes the shared connection, and the goal reports a time-out although it succeeded (3 of 3 runs; probably #318). With this branch the goal completes.
>
> One blocker: `tests/integration/test_actions.py::TestCancelActionGoal::test_cancel_request_sent` now fails on Humble, Jazzy and Lyrical. `cancel_action_goal` returns `{"error": "No active connection found for goal ID: ..."}` for a goal that this process did not start. That is a behavior change: before, the cancel was always forwarded to rosbridge. Two options:
> 1. keep the new behavior and update the test (and the tool description) to expect the error, or
> 2. fall back to the shared `ws_manager` when the goal is not in the registry, so a goal started by another client can still be cancelled.
>
> I prefer option 2, because it keeps the old contract. CI did not show this because fork PRs wait for approval to run.
>
> Smaller points:
> - `receive()` now calls `ws.recv()` outside `self.lock`. That is needed for cancel, but two threads that share the main `ws_manager` can now call `recv()` on the same socket at the same time. Is that possible with the other tools?
> - `receive()` treats only `WebSocketTimeoutException` as a timeout. #377 also handles the built-in `TimeoutError`. Its test `test_feedback_early_timeout_then_result_keeps_one_dispatch[builtin-timeout]` fails on this branch.

## #398: Use a millisecond ping timeout on macOS

**Recommendation: approve.**

### What I tested

- Unit tests: 22 passed. Integration (Jazzy): 113 passed, 1 skipped. Ruff clean.
- The new test fails on `develop` (`test_ping_uses_platform_specific_timeout[Darwin-2000]`), so it reproduces #394.
- Commands built with `ping_timeout=2.0`:
  - Linux: `ping -c 1 -W 2` (unchanged)
  - macOS: `ping -c 1 -W 2000`

- Not tested: a real macOS machine.

### Review comment

> Tested on Linux: the Linux and Windows commands are unchanged, and the macOS command now passes `-W 2000` for a 2 s timeout, which matches the BSD ping man page (`-W` is in milliseconds). The new test fails on develop and passes here. Ruff, unit and Jazzy integration tests pass. I could not run it on a Mac. LGTM.
>
